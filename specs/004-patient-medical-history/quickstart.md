# Quickstart: Validating Historia medyczna pacjenta

This guide proves the feature works end-to-end against the design in `data-model.md` and the
amended `../002-patient-records/contracts/patient-api.yaml`. It does not contain implementation
code — see `tasks.md` (generated by `/speckit-tasks`) for that.

## Prerequisites

- Local PostgreSQL (or Testcontainers-managed instance) with all migrations applied, including the
  two new ones this feature adds: `backend`'s `V13__audit_event_type_medical_history.sql` and
  `patient-service`'s `V3__medical_history.sql`.
- `auth-service` (`backend/`) and `patient-service` running locally, as in 002's quickstart
  Scenario 0 (unchanged session-sharing mechanism — this feature adds no new auth path).
- Frontend (`frontend/`) running locally with the new "Historia medyczna" tab on patient-detail.
- Seed data: the same four role accounts as 002's quickstart (`reception@clinic.test`,
  `doctor@clinic.test`, `assistant@clinic.test`, `admin@clinic.test`), plus one existing patient
  record with no medical-history entries yet (to exercise the empty-state requirement, FR-012).

## Scenario 1 — Alergie: dodanie, wyróżnienie krytycznej, brak przewijania (User Story 1, P1)

Maps to spec.md Acceptance Scenarios under User Story 1; unblocks
`specs/003-brand-ui-theme/tasks.md` T049.

1. As `doctor@clinic.test`, open a patient with no allergy entries.
   **Expect**: "Historia medyczna" tab shows "brak odnotowanych alergii" (FR-012), not an error or
   blank section.
2. `POST /patients/{id}/allergies` with `{substance: "Penicylina", reactionType: "Anafilaksja",
   severity: "CRITICAL"}`.
   **Expect**: `201`; the new entry appears immediately in the current list, rendered via
   `app-status-indicator` (`type="error"`, FR-006) — visible on the patient-detail screen without
   scrolling or any extra click (SC-004).
   Audit-logged as `MEDICAL_HISTORY_ENTRY_ADDED` (`metadata.entryType = ALLERGY`, `beforeState =
   null`).
3. As `reception@clinic.test`, open the same patient's basic-data view (`GET /patients/{id}`).
   **Expect**: `hasCriticalAllergyAlert: true` in the response, surfaced as a status-indicator
   badge in the patient header — but a direct `GET /patients/{id}/allergies` call from this role
   returns `404` (no access to substance/reaction detail, rbac-policy.md rule 7).
4. As `assistant@clinic.test`, `GET /patients/{id}/allergies`.
   **Expect**: `200`, same current-entry list a doctor would see (read parity, Clarifications
   Session 2026-08-29 Q3) — then attempt `POST /patients/{id}/allergies`.
   **Expect**: `404` (no write access, FR-004).

## Scenario 2 — Korekta w modelu append-only i "historia zmian" (FR-010, Clarifications Q1/Q2)

1. As `doctor@clinic.test`, `POST /patients/{id}/allergies` with `supersedesEntryId` set to the
   entry created in Scenario 1 step 2, and a corrected `severity: "MODERATE"`.
   **Expect**: `201`; the new entry is `recordStatus: CURRENT`; the old one flips to
   `recordStatus: SUPERSEDED` in the same transaction. Audit-logged as
   `MEDICAL_HISTORY_ENTRY_ADDED` with `beforeState` = the superseded entry's snapshot.
2. `GET /patients/{id}/allergies` (current-only, default view).
   **Expect**: only the corrected `MODERATE` entry appears — the superseded `CRITICAL` one is
   absent from the default view (Q2).
3. `GET /patients/{id}/allergies/history`.
   **Expect**: both entries appear, the superseded one clearly marked, `supersedesEntryId` linking
   the new row to the old. Audit-logged separately as `MEDICAL_HISTORY_HISTORY_VIEWED`.
4. Attempt any `PATCH`/`DELETE` against either allergy entry, as `doctor@clinic.test`.
   **Expect**: no such endpoint exists (append-only is enforced by the API surface itself, not
   just a convention).

## Scenario 3 — Leki (User Story 2, P2)

Maps to spec.md Acceptance Scenarios under User Story 2.

1. As `doctor@clinic.test`, open a patient with no medication entries.
   **Expect**: "brak odnotowanych leków" (FR-012).
2. `POST /patients/{id}/medications` with `{name: "Ibuprofen", dosage: "400mg 2x/dzień",
   startDate: "2026-08-01"}`.
   **Expect**: `201`; entry visible on the list with its start date; audit-logged as
   `MEDICAL_HISTORY_ENTRY_ADDED` (`metadata.entryType = MEDICATION`).
3. As `reception@clinic.test`, attempt `GET /patients/{id}/medications`.
   **Expect**: `404`.

## Scenario 4 — Choroby przewlekłe/przebyte, status kliniczny vs. status korekty (User Story 3, P3)

Maps to spec.md Acceptance Scenarios under User Story 3; verifies the two-independent-fields
decision from Clarifications Session 2026-08-29 Q1 / data-model.md.

1. As `doctor@clinic.test`, `POST /patients/{id}/chronic-conditions` with `{name: "Cukrzyca typu
   2", clinicalStatus: "ACTIVE", diagnosisDate: "2020-03-15"}`.
   **Expect**: `201`, `recordStatus: CURRENT`, `clinicalStatus: ACTIVE`.
2. Submit a correction: same entry, `supersedesEntryId` set, `clinicalStatus: "PAST"` (patient no
   longer has the condition, but the *record* isn't being fixed for an error).
   **Expect**: `201`; old entry `recordStatus → SUPERSEDED`; new entry `recordStatus: CURRENT,
   clinicalStatus: PAST` — proving `clinicalStatus` and `recordStatus` vary independently rather
   than one field controlling both meanings.

## Scenario 5 — RODO export includes full history (research.md #6)

1. As `doctor@clinic.test`, call `POST /patients/{id}/export` after Scenarios 1–4.
   **Expect**: `200`; the response's `allergies`/`medications`/`chronicConditions` arrays include
   **both** current and superseded entries (full history, not just the current view) — distinct
   from `GET /patients/{id}/allergies`, which stays current-only.
2. As `admin@clinic.test`, call the same export endpoint.
   **Expect**: `404` — unchanged from 002 (rbac-policy.md rule 6/7, no administrator clinical-data
   access, including this feature's data).

## Scenario 6 — Audit trail integrity (Principle III, research.md #2)

1. Perform one allergy add, one correction, one current-view read, and one history-view read from
   Scenarios 1–2.
   **Expect**: four rows in the shared `audit_log_entry` table (same hash chain 002's writes join,
   research.md #2/#8 of 002) — two `MEDICAL_HISTORY_ENTRY_ADDED`, one `MEDICAL_HISTORY_ENTRY_VIEWED`,
   one `MEDICAL_HISTORY_HISTORY_VIEWED` — each with `metadata.entryType = ALLERGY` and
   `target_patient_record_id` populated.
2. Attempt (as any role, including `ADMINISTRATOR`) to alter any of those rows via any application
   path.
   **Expect**: no such path exists — unchanged `SELECT, INSERT`-only grant on `audit_log_entry`.
