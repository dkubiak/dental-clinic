# Quickstart: Validating Interaktywny odontogram z rozpoznaniami i powierzchniami zębów

This guide proves the feature works end-to-end against the design in `data-model.md` and the
amended `../002-patient-records/contracts/patient-api.yaml`. It does not contain implementation
code — see `tasks.md` (generated by `/speckit-tasks`) for that.

## Prerequisites

- Local PostgreSQL (or Testcontainers-managed instance) with all migrations applied, including the
  two new ones this feature adds: `backend`'s `V14__audit_event_type_tooth_chart_diagnoses.sql`
  and `patient-service`'s `V4__tooth_chart_diagnoses.sql` (this migration drops `tooth_state`/
  `tooth_status` and seeds the diagnosis catalog).
- `auth-service` (`backend/`) and `patient-service` running locally, same session-sharing mechanism
  as 002/004's quickstarts — this feature adds no new auth path.
- Frontend (`frontend/`) running locally with the rewritten "Stan uzębienia" tab on patient-detail
  (`tooth-chart.component.ts` and its new child components, research.md D11).
- Seed data: the same four role accounts as 002/004's quickstarts
  (`reception@clinic.test`, `doctor@clinic.test`, `assistant@clinic.test`, `admin@clinic.test`),
  plus:
  - one **adult** patient record with no findings yet (exercises US1's empty state, FR-054),
  - one **child** patient record (date of birth < 6 years old, to exercise US5's default deciduous
    mode, FR-044).

## Scenario 1 — Lekarz odnotowuje rozpoznanie powierzchniowe (User Story 1, P1)

Maps to spec.md Acceptance Scenarios under User Story 1.

1. As `doctor@clinic.test`, open the adult patient's "Stan uzębienia" tab.
   **Expect**: both arches render with all teeth in "bez odnotowanych zmian" state, and a visible
   message that no findings exist for this patient (FR-054) — `GET
   /patients/{id}/tooth-chart` returns `200` with 32 `PERMANENT` positions all `presence: PRESENT`,
   no findings, `dentitionMode: PERMANENT`.
2. Select tooth 36 on the diagram.
   **Expect**: it becomes visibly selected; the detail panel opens showing FDI 36, "pierwszy
   trzonowiec dolny lewy", its enlarged surface map, zero canals, and an empty finding list
   (FR-005).
3. In the catalog search, pick "próchnica zębiny" (`anatomicalScope: SURFACE`), then attempt to
   save without picking a surface.
   **Expect**: the save is blocked client-side and server-side (`400` if forced directly against
   `POST /patients/{id}/tooth-chart/findings` with `surfaces` omitted) — FR-022.
4. Click the occlusal surface on the enlarged schema, then save
   (`diagnosisCatalogEntryId`, `surfaces: [OCCLUSAL_INCISAL]`, `diagnosisDate: today`).
   **Expect**: `201`; the new `ToothFinding` has `recordStatus: CURRENT`, `clinicalStatus: ACTIVE`,
   `authorRole: DOCTOR`; tooth 36 now renders as "z aktywnym rozpoznaniem" on the main diagram, and
   the occlusal zone shows a filled/highlighted state (not a letter, FR-029a). Audit-logged as
   `TOOTH_FINDING_ADDED` with `before_state: null`.
5. Reload the page (or open the same record as `assistant@clinic.test`).
   **Expect**: identical diagram state and identical finding content — `GET
   /patients/{id}/tooth-chart` is idempotent and role-symmetric between DOCTOR/ASSISTANT.
6. Select an incisor (FDI 11) and open its surface schema.
   **Expect**: an incisal surface option is offered instead of occlusal — the catalog/geometry
   layer never offers a surface that doesn't exist for the selected tooth type (FR-024, D11).
7. Pick a `WHOLE_TOOTH`-scope entry (e.g. "zapalenie miazgi nieodwracalne") on any tooth.
   **Expect**: the surface picker is hidden/disabled, and the save succeeds without any `surfaces`
   value (FR-023).

## Scenario 2 — Odczyt pełnego obrazu, warstwy i legenda (User Story 2, P2)

1. On a patient with several findings across different teeth/surfaces (from Scenario 1 plus a few
   more), open the tab as `doctor@clinic.test`.
   **Expect**: both arches render together; teeth with active findings are distinguishable by both
   color and a non-color cue (shape/pattern/outline — FR-039/FR-050).
2. Open the legend.
   **Expect**: every visual state currently in use on the diagram (position state, layer, surface
   symbol, canal color-coding) has a Polish-language explanation (FR-008).
3. Toggle the layer filter to "tylko rozpoznania".
   **Expect**: any "existing state" markers (e.g. a filling) dim/disappear; active diagnosis
   markers remain — `GET` is unaffected, this is a pure client-side filter (FR-009).
4. Open the history disclosure for a tooth with a resolved or superseded finding (produced in
   Scenario 3 below, revisit after running it once).
   **Expect**: resolved/superseded entries appear only under "historia zęba", never in the default
   current-findings list (FR-034).

## Scenario 3 — Korekta i zamknięcie rozpoznania (User Story 3, P2)

Exercises research.md D3 — close and correct are the same supersede primitive.

1. As `doctor@clinic.test`, close the finding created in Scenario 1 step 4:
   `POST /patients/{id}/tooth-chart/findings/{findingId}/close` with `{resolvedDate: today}`.
   **Expect**: `201`; response is a **new** `ToothFinding` with `clinicalStatus: RESOLVED`,
   `recordStatus: CURRENT`, `supersedesFindingId` = the original's id; the original now reads
   `recordStatus: SUPERSEDED` on `GET .../positions/36/history`. Tooth 36 stops showing "z
   aktywnym rozpoznaniem" on the main diagram. Audit-logged as `TOOTH_FINDING_ADDED` with
   `before_state` = the pre-close snapshot.
2. Immediately repeat the exact same `/close` call against the **original** (now-superseded)
   `findingId`.
   **Expect**: `409` — the partial unique index on `supersedesFindingId` blocks a second correction
   of an already-superseded finding (research.md D7); this is the mechanism, not just the outcome,
   that SC-010 requires.
3. On a different, still-active finding, correct a wrong surface via
   `POST .../findings/{findingId}/correct` with the fixed `surfaces` value.
   **Expect**: `201`; both the old (now `SUPERSEDED`) and new (`CURRENT`) versions remain visible
   in `.../history`, linked by `supersedesFindingId` — nothing is deleted or overwritten (FR-030).
4. As `assistant@clinic.test`, correct a finding originally created by `doctor@clinic.test`.
   **Expect**: `201`; `.../history` shows both authors against their respective versions, and the
   new version's `authorRole: ASSISTANT` (FR-058).

## Scenario 4 — Braki zębowe i stany specjalne (User Story 4, P3)

1. As `doctor@clinic.test`, set FDI 46 to `presence: EXTRACTED`:
   `PATCH /patients/{id}/tooth-chart/positions/46/presence` with the position's current
   `version` echoed as `expectedVersion`.
   **Expect**: `200`; tooth 46 renders as a missing-tooth state, visually distinct from both
   healthy and diseased teeth (FR-039).
2. Attempt to add a `SURFACE`-scope finding to FDI 46.
   **Expect**: `409` with an explanation (FR-040) — but adding an `allowedForMissingTooth` entry
   (e.g. "implant") to the same position succeeds (`201`, FR-041).
3. Retry step 1's presence `PATCH` reusing the **stale** `expectedVersion` from before the change.
   **Expect**: `409` (FR-070/SC-010) — proves the optimistic-lock path independently of the
   findings-correction path exercised in Scenario 3.
4. Add a root canal to a present tooth (FDI 26):
   `POST /patients/{id}/tooth-chart/positions/26/canals` with `{name: "MB2"}`.
   **Expect**: `201`; the canal renders inside the root silhouette on the main diagram with the
   `NEEDS_TREATMENT` color + non-color cue (FR-066a). Change its `state` to `TREATED`, then remove
   it (`DELETE .../canals/{canalId}`).
   **Expect**: removal is a `204` soft-delete (`removed: true`); if a finding referenced that
   canal, `.../history` still shows the reference, now flagged as pointing at a removed canal
   (FR-068) — never silently hidden.

## Scenario 5 — Uzębienie mleczne i mieszane (User Story 5, P3)

1. As `doctor@clinic.test`, open the **child** patient's tab for the first time.
   **Expect**: `GET .../tooth-chart` returns `dentitionMode: DECIDUOUS` by default (age-derived,
   FR-044); the diagram shows the 20 deciduous positions (51-85).
2. `PATCH .../dentition-mode` with `{dentitionMode: MIXED}`.
   **Expect**: `200`; both deciduous and permanent positions now render, visually distinguished
   (FR-046) — no existing finding is deleted or hidden (FR-047), confirmed by re-reading
   `.../positions/{fdi}/history` for any tooth with a prior finding.
3. Add a finding to a deciduous tooth (FDI 74).
   **Expect**: `201`, identical mechanics to Scenario 1 — deciduous positions are ordinary
   `ToothPosition` rows, not a special case (data-model.md).

## Scenario 6 — Zaznaczenie wielokrotne (User Story 6, P3)

1. As `doctor@clinic.test`, select FDI 41-46 (the lower anterior segment shortcut, FR-004b) and
   save one `WHOLE_TOOTH`-scope finding (e.g. "kamień nazębny") via
   `POST /patients/{id}/tooth-chart/findings/bulk` with `fdiNumbers: [41,42,43,44,45,46]`.
   **Expect**: `200`; `created` has 6 independent `ToothFinding` rows, each with its own `id` and
   audit entry (research.md D6) — not one shared record.
2. Include in the same `fdiNumbers` list a position previously set to `EXTRACTED` (Scenario 4).
   **Expect**: that position appears in `skipped` with a human-readable reason; the other 5 still
   succeed in `created` — the call never fails wholesale (FR-004a, US6 scenario 3).
3. Correct one of the six created findings independently
   (`POST .../findings/{findingId}/correct`).
   **Expect**: only that one finding gets a new version; the other five are untouched — proving
   independence (US6 scenario 2).

## Scenario 7 — RBAC, deny-404, and audit trail (FR-057/FR-059/FR-060, research.md D8/D9)

1. As `reception@clinic.test`, call `GET /patients/{id}/tooth-chart` directly.
   **Expect**: `404` — identical to a nonexistent patient id, revealing neither clinical content
   nor the fact that findings exist (FR-059, rbac-policy.md rule 2/8).
2. As `admin@clinic.test`, call the same endpoint.
   **Expect**: `404` — no routine administrator clinical access (rbac-policy.md rule 3/6/8).
3. Inspect the shared `audit_log_entry` table after Scenarios 1-6.
   **Expect**: one `TOOTH_CHART_VIEWED` row per read, one `TOOTH_FINDING_ADDED` row per
   create/close/correct/bulk-item, one `TOOTH_POSITION_PRESENCE_CHANGED`,
   `DENTITION_MODE_CHANGED`, `ROOT_CANAL_ADDED`/`ROOT_CANAL_CHANGED`/`ROOT_CANAL_REMOVED` row per
   respective operation — every one with `target_patient_record_id` populated and, for writes, a
   populated before/after snapshot (FR-060). No row is ever updatable/deletable through any
   application path (Principle III, unchanged mechanism).

## Scenario 8 — RODO export, accessibility, and manual-only checks

1. As `doctor@clinic.test`, call `POST /patients/{id}/export`.
   **Expect**: `200`; the `toothChart` field includes all 52 positions, all canals (including
   removed ones), and the **full** finding history — current, resolved, and superseded alike, with
   catalog entries resolved to Polish names, not bare codes (FR-061).
2. **Manual check (not automatable, documented here rather than skipped)**: with a screen reader
   and keyboard only, navigate teeth with arrow keys, open the detail panel, pick a surface, and
   save a finding without touching a pointing device (FR-052/FR-053/SC-007).
3. **Manual check**: at 320×568px, confirm both arches are usable, no 44×44px touch target is
   smaller than required, and the page itself never scrolls horizontally (SC-004) — same accepted
   Playwright-coverage gap 004 documented for its own SC-004 (plan.md, "Known coverage
   limitations").
4. **Manual check (SC-009, human-subjects, out of any automated suite by definition)**: with ≥5
   doctors, present a populated odontogram and confirm ≥90% correctly read every marking using only
   the in-app legend, no prior training.
