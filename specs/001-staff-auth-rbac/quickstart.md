# Quickstart: Validating Staff Auth & RBAC

This guide proves the feature works end-to-end against the design in `data-model.md` and
`contracts/`. It does not contain implementation code — see `tasks.md` (generated by
`/speckit-tasks`) for that.

## Prerequisites

- Local PostgreSQL (or Testcontainers-managed instance) with the Flyway migrations for the tables
  in `data-model.md` applied.
- Backend service (`backend/`) running locally, configured with a local/dummy AWS SES sender for
  password-reset emails (e.g. captured to a local mail-catcher rather than sent for real) and a
  local KMS-equivalent (e.g. LocalStack) for the encrypted MFA secret column.
- Frontend (`frontend/`) running locally against the local backend.
- Seed data: three staff accounts, one per role, each with MFA enrollment already completed so
  login scenarios can be validated without walking through enrollment UI each time:
  - `reception@clinic.test` / role `RECEPTION`
  - `doctor@clinic.test` / role `DOCTOR`
  - `admin@clinic.test` / role `ADMINISTRATOR`

## Scenario 1 — Role-scoped login (User Story 1, P1)

Maps to spec.md Acceptance Scenarios 1–6 under User Story 1.

1. Log in as `reception@clinic.test` with correct password + TOTP code.
   **Expect**: redirected to the appointments/contact-details home screen; a direct request to a
   medical-records endpoint (`contracts/auth-api.yaml` — any doctor-only resource) returns `404`.
2. Log in as `doctor@clinic.test`.
   **Expect**: access to medical records/treatment history for a patient *not* specifically
   assigned to this doctor succeeds (FR-014 — role is the only boundary).
3. Log in as `admin@clinic.test`.
   **Expect**: access to `/accounts` and `/audit-log` succeeds; a direct request to any
   patient-clinical-data endpoint returns `404` (no default clinical access).
4. Attempt login with a correct email and wrong password.
   **Expect**: `401`, and the error message does not reveal whether the email or password was
   wrong.
5. As `reception@clinic.test`, request a `DOCTOR`-only resource directly (bypassing the UI, e.g.
   `curl` the endpoint with the reception session cookie).
   **Expect**: `404`, not `403` (research.md #8).
6. Submit correct email + password but omit/submit a wrong TOTP code at `/auth/mfa/verify`.
   **Expect**: `401`; no session cookie is set; account remains unauthenticated.
7. Use `/auth/password-reset/request` for `reception@clinic.test`, retrieve the emailed (or
   mail-catcher-captured) link, follow it, set a new password, then log in with the new password.
   **Expect**: success end-to-end; the link is rejected if reused (single-use, FR-016).

## Scenario 2 — Audit log completeness & immutability (User Story 2, P2)

Maps to spec.md Acceptance Scenarios under User Story 2.

1. Perform one successful login and one failed login (wrong password) for the same account.
   **Expect**: `GET /audit-log` (as admin) shows two entries — `LOGIN_SUCCESS` and
   `LOGIN_FAILURE` — each with the account id, timestamp, and outcome, and neither entry contains
   the plaintext password.
2. As admin, change `doctor@clinic.test`'s role to `ADMINISTRATOR` and back to `DOCTOR`.
   **Expect**: two `ROLE_CHANGED` entries, each with `before_state`/`after_state` matching the
   role values, and the actor set to the admin account.
3. Attempt to modify or delete any existing audit log row — via the API (no such endpoint exists
   in `contracts/auth-api.yaml`) and, as a defense-in-depth check, via a direct SQL `UPDATE`/
   `DELETE` using the application's own DB role/credentials.
   **Expect**: no API path exists at all; the direct SQL attempt fails with a permission error
   (research.md #7 — `UPDATE`/`DELETE` revoked at the grant level).
4. Recompute the `entry_hash` chain across all rows (`previous_entry_hash` linkage) and confirm it
   validates with no gaps — proves tamper-evidence independent of the application layer.

## Scenario 3 — Admin account lifecycle (User Story 3, P3)

Maps to spec.md Acceptance Scenarios under User Story 3.

1. As admin, `POST /accounts` a new staff account with role `RECEPTION`.
   **Expect**: `201`; the new account can complete first-login MFA enrollment and then log in with
   reception-scoped access.
2. As admin, `POST /accounts/{id}/deactivate` for that account.
   **Expect**: subsequent login attempt for that account returns `403` (deactivated) and produces
   a `LOGIN_DENIED_DEACTIVATED` audit entry (US3 AC2).
3. As admin, attempt to open a medical-record or treatment-history resource directly without any
   special grant.
   **Expect**: `404` (US3 AC3 — no default clinical access even for administrators).

## Success criteria check

Re-verify against spec.md Success Criteria after running the scenarios above:
- SC-001: time from correct credentials (incl. MFA) to role-appropriate home screen < 10s.
- SC-002: every out-of-role attempt across Scenarios 1 & 3 returned a denial (`404`), zero
  exceptions.
- SC-003: every audit entry from Scenario 2 was queryable via `/audit-log` within 1 minute (in
  practice: immediately, since the write is synchronous — research.md #7).
- SC-004: zero successful tamper attempts in Scenario 2 step 3.
- SC-005: the account created in Scenario 3 step 1 was fully functional in under 2 minutes.
- SC-007: the reset flow in Scenario 1 step 7 completed in under 5 minutes without admin
  involvement.
